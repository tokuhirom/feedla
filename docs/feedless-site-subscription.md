# フィード非提供サイトの購読機能 — 方針検討ドキュメント

ステータス: **検討中(未決定)**。[DESIGN.md の未決事項 #1](DESIGN.md#未決事項--今後の検討)
（フィード内の全文取得）と技術的な土台（本文抽出）を共有するが、本ドキュメントは
「そもそも RSS/Atom を配信していないサイト」を購読対象にする、より広いスコープを扱う。

## 背景・課題

feedla は LDR/Fastladder 的な「大量のフィードを高速に読み流す」体験を目指しているが、
昨今は RSS/Atom を配信しないサイト（企業ブログ、ニュースサイトの一部、個人サイト等）が
増えている。これらも同じ 3 ペイン UI・同じ未読管理の中で読めるようにしたい、というのが要望。

前提として **外部 SaaS は利用しない**（自前のシングルバイナリ内で完結させる）。

## 想定する対象サイトの具体例

方式の優劣は対象サイトの性質に強く依存するため、代表的なパターンを先に挙げる。
以降の比較・優先度づけはこれらへの対応可否を基準に判断する。

| # | 対象サイトの性質 | フィード有無 | 例になりそうな構造 |
|---|---|---|---|
| 1 | 企業のお知らせ / プレスリリース一覧ページ | フィードなし、または壊れている | 一覧テーブル or カード。SSR（サーバレンダリング）。 |
| 2 | 個人ブログ（静的サイトジェネレータ製、フィード配信忘れ） | フィードなし | 一覧はあるが、実は `/feed/index.xml` 等が存在しているだけの場合もある |
| 3 | ニュースサイトの特定コーナー（トップは動くが特集面はフィード非対応） | 一部のみフィードなし | 一覧＋ページネーション |
| 4 | SPA で構築された企業サイトのお知らせページ | フィードなし | クライアントサイドレンダリング、素の GET では一覧が空 |
| 5 | 更新日のない 1 枚もののステータスページ（障害情報・FAQ 等） | 概念的にフィード不要 | 一覧ではなく単一ページの内容が書き換わる |

- パターン 1〜3 は「一覧から新着記事を拾う」ニーズ（方式 B 系統が本命）。
- パターン 4 は素の HTTP GET が効かない（方式 E が必要、または対象外として諦める）。
- パターン 5 は「一覧」ではなく「1 ページの差分」（方式 A が本命）。

**重要な前提**: パターン 1〜3 が本来のユースケースの大半を占めると見られる。
パターン 5 は方式 A で救えるが対象範囲が狭く、方式 A だけを実装しても「新しいサイトを
何でも読めるようになった」という体感には直結しない点に注意する（後述の優先度に反映）。

## 参考にした先行事例

- [Feedly RSS Builder](https://64p.org/notes/feedly-rss-builder.html) — プレビュー上で
  「フィード化したい記事セクション」をクリックして選択する GUI。CSS/XPath を手で書かせない
  代わりに、対話的な要素選択に倒している。JS 動的サイトは非対応、Safari 非対応など制約は多い。
- [HTML コンテンツ抽出技術](https://64p.org/notes/html-content-extraction.html) —
  Arc90 Readability（DOM ノードにスコアを付けて最高得点領域を本文とみなす）、
  ExtractContent（「本文を当てる」でなく「本文以外を除外する」逆転の発想。日本語サイト向け）、
  Trafilatura/readability-lxml/Newspaper4k（現代的な Python 実装）。
- [RSS-Bridge](https://github.com/RSS-Bridge/rss-bridge) — サイトごとに専用の
  「Bridge」クラス（スクレイパー）を書く形式。汎用アルゴリズムではなく、サイト固有のコードを
  人手でメンテする前提。`FeedExpander` という共通ヘルパはあるが、基本は 1 サイト 1 実装。
- [urlwatch](https://urlwatch.readthedocs.io/) / [changedetection.io](https://github.com/dgtlmoon/changedetection.io) —
  「フィード生成」ではなく「変更検知」が主目的のツール。CSS/XPath でスコープを絞り、
  フィルタパイプラインを通した結果のスナップショットを保存し、次回取得時との diff を
  イベントとして扱う。changedetection.io は差分を Atom/RSS として出力するモードも持つ。
  日付・カウンタ・広告枠のような「本文とは無関係だが毎回変わる要素」をどう除外するかの
  フィルタ（正規表現置換、要素除外）が urlwatch の設定の大半を占めており、
  **変更検知の実運用における難所はここ**だと分かる。
- [Feed43](https://feed43.com/) のような「サンプル HTML から抽出テンプレートを推測する」
  タイプのツール — GUI クリック選択ほどリッチではないが、リンクの URL パターン
  （正規表現）とテキストの相対位置だけで一覧を抽出する、より軽量な中間的アプローチ。
- MDR (Mining Data Records) 等の学術的手法 — DOM 木を「タグ列の文字列」とみなし、
  文字列照合で類似する兄弟ノード列（＝一覧の各アイテム）を自動検出する。一覧ページの
  「繰り返し構造」を教師データなしで見つけるアプローチ。ただし記録同士が隣接していない
  レイアウトには弱い。

## 方式の選択肢

### A. 単一記事ページの本文抽出＋差分検知（urlwatch 型）

ユーザーが記事一覧ページではなく **個別ページ、または更新される 1 ページ**（お知らせページ等）
を登録し、定期取得のたびに Readability 相当で本文抽出→正規化→ハッシュ化し、前回との差分が
あれば「更新」を 1 エントリーとして記録する。上記の対象サイト例ではパターン 5 のみが対象。

- 長所: 既存の `feeds.body_hash` と同じ発想（body_hash は既に DESIGN.md にある）で、
  フィード取得パイプラインへの統合コスト自体は低い。
- 短所:
  - **「一覧ページの新着記事」を扱えない**。1 URL = 1 エントリー着地点なので、
    ブログのトップページを登録しても記事ごとに独立したエントリーにはならない。
  - 「実装が最も軽い」という評価は本文抽出パイプラインの配線だけを見た場合の話で、
    **実運用の難所は誤検知抑制**。日付表示・アクセスカウンタ・「関連記事」枠・広告のような
    「本文の一部だが実質ノイズ」な要素が変わるだけで毎回差分ありと判定してしまう。
    urlwatch がフィルタパイプライン（正規表現除去・要素除外）に多くの機能を割いているのは
    まさにこの問題への対処であり、Readability で本文領域を絞ったとしても解決しきれない。
    体感の実装難易度は「配線コスト」より「誤検知抑制コスト」で決まると見た方がよい。

### B0. 構造化データの活用（sitemap.xml / schema.org / microformats）

DOM スクレイピングに入る前段として、サイトが既に持っている構造化データを使えないか確認する。

- **sitemap.xml**: `lastmod` 付きの URL リストを提供しているサイトは多く、
  前回取得時からの差分 URL（新規 URL、または `lastmod` が更新された URL）だけを
  「新着候補」として拾える。DOM 構造に依存しないため、マークアップ変更に強い。
  ただし `lastmod` の正確性はサイト次第（更新していないサイトも多い）。
- **schema.org / JSON-LD（`Article`, `NewsArticle`, `BlogPosting` 等）/ OGP**:
  一覧ページの各カードに構造化データが埋め込まれていれば、DOM の見た目に依存せず
  タイトル・URL・公開日を機械的に取り出せる。ニュースサイトでは普及率が比較的高い。
- 長所: DOM の繰り返しパターンを推測する必要がなく、B1/B2 よりも壊れにくい。
  実装も「構造化データのパーサ」で済み、B1 の GUI や B2 のクラスタリングより軽い。
- 短所: **構造化データを持たないサイトには無力**（個人ブログ等では期待薄）。
  万能ではなく、あくまで B1/B2 の前段のショートカットとして機能する。
- 位置づけ: DOM ベースの抽出（B1/B2）に進む前に、まずここを試すフォールバックの
  1 段階として組み込む価値がある。ただし本ドキュメントでは「実装を先にやるべき」とまでは
  主張しない。効果はサイト依存が大きく、実際にどの程度のサイトで拾えるかは未検証。

### B. 一覧ページからの構造化リスト抽出（Feedly RSS Builder 型）

一覧ページ（ブログのトップ、ニュースの一覧）から「記事カード」に相当する繰り返し要素を
検出し、各要素からタイトル・リンク・（あれば）日付・サムネイルを取り出して仮想的な
フィードを合成する。対象サイト例のパターン 1〜3 が主な守備範囲。要素の検出は 3 通り考えられる：

- **B1. ユーザーが GUI でクリック選択**（Feedly RSS Builder 方式）。初回登録時にプレビューを
  見せ、「これが記事タイトルです」とクリックしてもらい、その要素の CSS セレクタ
  （またはその祖先の中で最も安定していそうなクラス／構造）を推定して保存する。
  以降のクロールはこのセレクタで一覧を再取得する。
  **実装コストの注意**: 「セレクタを保存して再利用する」部分は軽いが、
  「取得した第三者サイトの HTML を安全にプレビュー表示し、クリックで要素を拾う」
  という GUI そのものは軽視できないコストになる。取得元 HTML をそのまま iframe 表示
  すれば任意の script が動きかねないため、サニタイズ・サンドボックス化・元サイトの
  CSS を壊さない程度の整形が要る。DESIGN.md の CSP・bluemonday 方針と同様の慎重さが必要。
- **B1.5. URL パターンフィルタ（Feed43 型、GUI 不要の中間形態）**。一覧ページ内の
  `<a>` タグを全て抽出し、リンク先 URL の正規表現パターン（例: `/blog/\d{4}/\d{2}/.+`）と
  リンクテキストの非空判定だけで「記事リンクらしきもの」を絞り込む。CSS セレクタや
  DOM 構造には依存しないため B1 の GUI ほど作り込みが要らず、B2 ほど誤爆もしにくい
  （URL パターンはサイト運営者が意図的に決めている規則性なので、繰り返し DOM 構造の
  推測より当てやすい場合がある）。ユーザーには「記事 URL のパターンを正規表現で
  入力してもらう」程度の軽い UI で足りる。B1 と B2 の間を埋める現実的な選択肢として
  優先度を上げて検討する価値がある。
- **B2. 自動検出**（MDR 的アプローチ）。DOM 木を走査し、類似構造を持つ兄弟ノード列
  （タグ名・クラス・深さのパターンが一致する繰り返し）をスコアリングして一覧候補を
  自動抽出する。ユーザー操作なしで動く可能性がある一方、精度は落ちる（ナビゲーションや
  広告枠を誤検出するケースがある）。

一覧から得られるのは「タイトル＋リンク」までで、本文は別途 **各記事の個別ページを
取得して A の本文抽出をかける（2 段階クロール）** ことになる。RSS が本来配信する情報量に
一番近いのはこの方式。

- 長所: 「新しい記事が増えた」を自然にエントリー単位で表現できる。RSS 本来の体験に最も近い。
  対象サイト例のパターン 1〜3 をカバーできる、本ドキュメントの中では守備範囲が最も広い方式。
- 短所: 実装コストが高い（特に B1 の GUI）。個別記事ページも毎回追加で fetch するため
  通信量・サイトへの負荷が A より大きい（1 サイトあたり 1 リクエストではなく 1+N リクエスト）。
  セレクタ・URL パターンがサイトのマークアップ変更で壊れやすく、**壊れたことをどう検知して
  ユーザーに知らせるか**の設計が追加で要る。

### C. サイト固有スクレイパー（RSS-Bridge 型）

汎用アルゴリズムに頼らず、サイトごとに小さな抽出ロジック（Go の struct + 関数、または
YAML/JSON 設定）を都度書く。RSS-Bridge の哲学に近い。

- 長所: 対応済みサイトでは精度が最も高く、壊れにくい（メンテされていれば）。
- 短所: 「フィードのないサイトを購読したい」というエンドユーザーの one-off なユースケースに
  対し、事前にコードを書く必要があるのはミスマッチ。feedla は自分専用ツールなので
  コミュニティでレシピを共有する RSS-Bridge のようなスケールメリットが働かない。
  B1/B1.5（ユーザー自身によるセレクタ／パターン指定）を実装すれば、結果的に
  「ユーザー自身が書く軽量なレシピ」としてこの方式を包含できるとも言える。

### D. LLM による抽出

一覧ページの HTML（または簡略化した DOM）を LLM に渡し、記事一覧の CSS セレクタ、
あるいは直接タイトル＋リンクの JSON を生成させる。

- **「外部 SaaS は利用しない」という前提と抵触する**（ローカル LLM を使わない限り、
  外部 API 呼び出しになる）。feedla の「シングルバイナリ・低リソース・外部依存ゼロ」という
  設計目標（DESIGN.md 冒頭）とも根本的に矛盾する。
- ローカル LLM（llama.cpp 等の埋め込み）は数百 MB〜数 GB のモデルが必要で、「RAM 100MB
  以下」という現行目標を大きく超える。
- 結論として **今回のスコープからは除外**。将来オプトインの外部連携機能として切り出すなら
  別途検討する、という位置づけに留める。

### E. ヘッドレスブラウザでのレンダリング（JS 動的サイト対応）

SPA やクライアントサイドレンダリングのサイト（対象サイト例のパターン 4）は、
素の HTTP GET では本文どころか一覧すら取得できない。Playwright/Chromium 等の
ヘッドレスブラウザで一度レンダリングしてから A/B の抽出をかける必要がある。

- 長所: 対応できるサイトの幅が大きく広がる。
- 短所: Chromium バイナリの同梱・プロセス管理・メモリ使用量（1 タブ数十〜百数十 MB）は
  「シングルバイナリ・低リソース」という feedla の中核目標と真っ向から衝突する。
  fetch 1 回のコストが RSS 取得の 100 倍以上になり得る。
- 結論として **今回のスコープからは除外**。パターン 4 のサイトは当面「対応できない」と
  割り切る。

## 推奨方針（段階的実装案）

Fable によるレビューで「単一ページ監視（方式 A）だけでは本来の要望（一覧の新着を
記事単位で読みたい）に応えられず、これを最初に作っても価値検証にならないリスクがある」
という指摘を受け、当初案（A → B1 → B2）から **B 系統を優先する順序に見直した**。

既存の `internal/feed/discover.go` の「フィード自動検出」フローで候補が 0 件だった場合の
拡張として組み込む（DESIGN.md のフィード自動検出は現状ステップ 1〜4 のみで、候補 0 件は
エラーを返す。共通パスへの推測フォールバックのような案は採用しない）。

1. **Phase F1: 一覧ページ抽出（方式 B1.5、URL パターンフィルタ）を最初に実装する。**
   - 対象サイト例 1〜3（本来の要望の中心）を最小コストでカバーできる方式を優先する。
   - 一覧ページの `<a>` を抽出し、ユーザー指定の URL 正規表現とリンクテキスト非空判定で
     記事候補を絞り込む。GUI クリック選択（B1）より実装コストが小さく、まずここで
     「一覧 → 新規 URL 検出 → 個別記事 fetch → 本文抽出」という 2 段階パイプラインの
     骨格を作る。
   - 本文抽出には `go-shiori/go-readability`（Go 製、Mozilla Readability 移植）を使う。
   - `subscriptions` に `list_url_pattern` 相当のカラムを追加する程度で既存スキーマに
     乗せられる。既知 URL は本文取得済みならスキップし、新規 URL のみ fetch する。
   - セレクタ／パターンが空振り（0 件 or 全件変化なし連発）した場合に `error_count` 的な
     仕組みで検知し、UI 上で「パターンが機能していないかもしれません」と警告する。
2. **Phase F2: GUI クリック選択（方式 B1）を追加する。**
   - B1.5 の正規表現指定が難しい・馴染まないサイト向けに、プレビュー上でのクリック選択
     UI を追加する。取得済み HTML の安全な表示（サニタイズ・サンドボックス化）が
     このフェーズの主な作り込みポイントになる。
3. **Phase F3: 単一ページ監視（方式 A）を追加する。**
   - 対象サイト例のパターン 5（ステータスページ等）向け。カバー範囲は狭いが、
     `feeds.body_hash` と同様の発想で実装コスト自体は低いため、B 系統の後回しにしても
     過度な負担にはならない。
   - 実装時は「配線コスト」より「誤検知抑制コスト」（日付・カウンタ・広告等の
     ノイズ差分の除外）に時間を割く前提で見積もる。
4. **Phase F4（任意・保留）: 自動検出（方式 B2 / MDR 的手法）でセレクタ／パターン指定の
   手間を減らす。**
   - 実装コストが高く精度検証も要るため、F1〜F3 が実運用されてから着手する。
5. **B0（構造化データ活用）は F1 の実装時に、一覧ページ取得の前段で sitemap.xml /
   JSON-LD の有無を軽くチェックする形で拾えるなら拾う、程度の位置づけに留める。**
   単独のフェーズとして先出しするほどの優先度・効果検証はまだできていない。
6. **方式 C（サイト固有コード）・D（LLM）・E（ヘッドレスブラウザ）は現時点で不採用。**
   - C は B1/B1.5 が実質的に「ユーザーが自分で書く軽量レシピ」を提供するため、当面は
     エッジケース対応の作り込みポイントとして温存する程度で良い。
   - D は「外部 SaaS 不使用」という前提と衝突するため対象外。
   - E は低リソース目標と衝突するため対象外（対象サイト例のパターン 4 は諦める）。

## 未解決の論点

- **一覧ページの「新着」判定基準**: URL の初出だけで十分か、それとも一覧内の並び順・
  日付要素も見るか。並び順が変わるサイト（おすすめ順など）では URL 初出だけでは
  誤検知しやすい。
- **本文抽出の失敗時の扱い**: 抽出結果が空 or 極端に短い場合、フォールバックとして
  一覧ページのスニペット（タイトル＋リード文）だけをエントリー本文にするか。
- **サイト側への配慮**: robots.txt の尊重、`Crawl-delay` 相当の解釈、`noai`/`noindex`
  的なメタタグをどう扱うか（フィード配信サイトと違い、相手はスクレイピングを
  前提にしていない）は要検討。DESIGN.md の SSRF 対策・礼儀（同一ホスト同時接続数 2、
  最低 1 秒間隔）は流用できるが、フィード取得より訪問間隔をさらに緩めるべきかもしれない。
- **著作権・利用規約上の整理**: 個人の自分専用ツールとはいえ、本文全体を保存・全文検索
  対象にすることの妥当性（RSS 配信サイトと違い、サイト運営者が「全文配信」を意図して
  いない）。少なくとも UI 上でユーザーに注意喚起する、程度は必要かもしれない。
- **UI/UX**: 3 ペイン UI・pin・全文検索など既存機能への統合は自然にできそうだが、
  「フィード購読」と「ページ監視／一覧抽出購読」を UI 上どう区別して見せるか
  （アイコンで区別する程度で十分か）は未検討。
- **エントリーの `guid` 設計との衝突**: 方式 A（単一ページ監視）は同一 URL を
  繰り返し取得する構造のため、既存の `UNIQUE(feed_id, guid)`（entries テーブル）に
  そのまま乗せると「同じ URL＝同じ guid」で新規エントリーとして insert できない。
  差分検知のたびに guid を変える（例: `hash(url + fetched_at)` や連番）などの
  設計変更が必要で、既存の「同一 feed 内で url 一致 かつ hash 一致なら同一とみなす」
  重複判定ロジックとも整合を取る必要がある。
- **OPML バックアップとの整合性**: DESIGN.md は「最悪 DB を捨てて OPML から
  再構築できる」ことをバックアップ戦略の一部としているが、OPML はフィード URL しか
  表現できない。B 系統のセレクタ／URL パターン設定や A の監視対象ページ設定は
  OPML に round-trip できないため、これらの設定も含めた別途のエクスポート／
  インポート手段（例: JSON 設定のバックアップ）を検討する必要がある。
- **bot 対策への現実的な期待値**: Cloudflare 等の bot 対策が入っているサイトは
  素の HTTP GET が 403 で弾かれることがある。fetch 頻度や User-Agent を礼儀正しく
  しても回避できないケースがあり、「対応できないサイトがある」ことを機能の前提として
  明示しておく（回避策を積極的に講じる方針は取らない）。
- **charset 判定**: 既存のフィード取得は `gofeed`（内部で `goxpp`）が charset 判定を
  肩代わりしているが、HTML スクレイピングでは feedla 自身が `Content-Type` ヘッダや
  `<meta charset>` を見て判定する必要がある（`golang.org/x/net/html/charset` の導入を
  検討）。Shift_JIS/EUC-JP の古い日本語サイトが対象に含まれる可能性を考えると軽視できない。
- **DESIGN.md の未決事項 #1**（フィード内の全文取得）と本文抽出ロジックを共有できる
  可能性が高い。実装するタイミングを合わせて一体で設計するとコードの再利用効率が良い。
